# AI Meeting Intelligence

Браузерный прототип, который превращает запись разговора не в обычное резюме встречи, а в **финальное состояние договорённостей**.

Система определяет:

- принятые задачи;
- ответственных;
- финальные дедлайны;
- отменённые задачи;
- отклонённые предложения;
- нерешённые вопросы;
- отсутствующего ответственного или срок;
- подтверждающую цитату;
- таймкод этой цитаты.

Для каждого результата можно прослушать соответствующий фрагмент исходной аудиозаписи.

---

# Что делает прототип

Во время реального разговора одна и та же договорённость может несколько раз меняться.

Например:

1. Сначала предлагается задача.
2. Кто-то берёт её на себя.
3. Согласовывается дедлайн.
4. Позже дедлайн меняется.
5. Другая задача отменяется.
6. Ещё одно предложение отклоняется.
7. По некоторым вопросам ответственный или срок так и не определяются.

Обычное резюме встречи может сохранить уже устаревшую информацию.

Цель этого прототипа — ответить на более конкретный вопрос:

> Каково финальное состояние договорённостей к концу разговора?

---

# Основные возможности

Прототип умеет:

- принимать MP3-запись разговора;
- распознавать двух спикеров;
- получать текст разговора с таймкодами;
- извлекать события и изменения договорённостей;
- определять финальное состояние задач;
- учитывать исправленный дедлайн;
- учитывать отмену задачи;
- учитывать отклонённое предложение;
- не придумывать отсутствующего ответственного;
- не придумывать отсутствующий дедлайн;
- сохранять относительные даты вроде `на следующей неделе`;
- отмечать отсутствие контекста даты;
- показывать подтверждающую цитату;
- показывать таймкод;
- воспроизводить соответствующий фрагмент аудио;
- не превращать условное намерение в подтверждённую задачу.

---

# Пример

Разговор:

```text
Оксана:
Я возьму оптимизацию изображений.

Артём:
Сможешь закончить к пятнице?

Оксана:
Да.

...

Оксана:
К пятнице не успеваю. Давай перенесём на понедельник.

Артём:
Хорошо, тогда понедельник — новый дедлайн.
```

Финальный результат:

```text
Задача: оптимизация изображений
Ответственный: Оксана
Дедлайн: понедельник
```

Старый дедлайн `пятница` не остаётся финальным.

---

# Архитектура

Пайплайн разделён на три основные стадии.

```text
Аудио
  ↓
AssemblyAI
Speech-to-text + speaker diarization + timestamps
  ↓
Ollama / qwen2.5:7b
Извлечение хронологических событий
  ↓
Deterministic Python resolver
Определение финального состояния + evidence alignment
  ↓
Flask UI
Финальные договорённости + воспроизведение аудиодоказательства
```

---

# 1. Распознавание речи

Для расшифровки используется:

**AssemblyAI**

Стадия распознавания возвращает:

- текст разговора;
- speaker labels;
- таймкоды;
- структуру реплик по спикерам.

В текущем прототипе предполагается один язык внутри одной записи.

---

# 2. AI-анализ

Транскрипт анализируется локально через:

**Ollama**

Модель:

```text
qwen2.5:7b
```

LLM не формирует финальный ответ напрямую.

Его задача — извлечь хронологические события, например:

- задача упомянута;
- назначен ответственный;
- назначен дедлайн;
- дедлайн изменён;
- задача отменена;
- предложение отклонено;
- вопрос остался нерешённым.

Полученные события сохраняются в:

```text
events_v5.json
```

---

# 3. Deterministic resolver

После извлечения событий финальное состояние определяется обычным Python-кодом.

Основной файл:

```text
resolve_v5_evidence.py
```

Resolver:

- объединяет события одной задачи;
- применяет более поздние изменения поверх ранних;
- сохраняет последний согласованный дедлайн;
- исключает отменённые задачи из активных;
- отделяет отклонённые предложения;
- сохраняет нерешённые вопросы;
- не придумывает owner;
- не придумывает deadline;
- сохраняет относительные даты;
- отмечает отсутствие date context;
- привязывает supporting quote к реальному таймкоду транскрипта;
- нормализует некоторые варианты названий одной и той же темы.

---

# Почему финальное состояние определяется не вторым LLM-вызовом

Во время разработки использовалась схема с дополнительным LLM-проходом для формирования финального результата.

Она оказалась менее стабильной.

Например:

```text
Friday
↓
исправлено на Monday
```

после второго AI-прохода иногда снова превращалось в:

```text
Friday
```

То есть модель могла восстановить уже устаревшее состояние.

Поэтому текущая архитектура разделяет ответственность:

```text
LLM:
понимание естественного языка и извлечение событий
```

```text
Python:
переходы состояний и определение финального результата
```

Это делает систему более предсказуемой и удобной для тестирования.

---

# Evidence-first подход

Каждый итоговый элемент содержит:

- название задачи или вопроса;
- финальный статус;
- ответственного, если он известен;
- дедлайн, если он известен;
- supporting quote;
- timestamp.

В интерфейсе есть кнопка:

```text
▶ Прослушать
```

После нажатия браузер:

1. перематывает исходную запись на нужный таймкод;
2. запускает воспроизведение;
3. останавливает его в конце соответствующего сегмента.

Это позволяет проверять вывод системы непосредственно по исходной записи.

---

# Работа с неоднозначностью

Система специально ведёт себя консервативно.

Пример:

```text
Оксана:
Я, возможно, посмотрю завтра, если закончу текущие задачи.

Артём:
Хорошо. Тогда пока не фиксируем это за тобой.
```

Система не должна превращать это в:

```text
Ответственный: Оксана
Дедлайн: завтра
```

Такой вопрос должен остаться нерешённым.

---

# Работа с относительными датами

Если в разговоре сказано:

```text
на следующей неделе
```

но нет достаточного календарного контекста, система не превращает это в придуманную дату.

Результат сохраняется примерно так:

```text
Дедлайн: на следующей неделе
Не хватает: date_context
```

# AssemblyAI API key

Для распознавания речи требуется API key AssemblyAI.

API key не хранится в исходном коде и не должен коммититься в GitHub.

Перед запуском приложения в PowerShell необходимо задать переменную окружения:

```powershell
$env:ASSEMBLYAI_API_KEY="YOUR_API_KEY"
```

Вместо `YOUR_API_KEY` необходимо указать собственный AssemblyAI API key.

После закрытия текущего окна PowerShell эта временная переменная окружения перестанет действовать.

В `transcribe.py` используются:

```text
speaker_labels=True
language_code="ru"
```

Конкретная AssemblyAI speech model в коде явно не зафиксирована.

# Производительность

На текущей машине главным bottleneck является:

```text
Ollama + qwen2.5:7b
```

При работе на CPU анализ может занимать несколько минут.

На этапе прототипа приоритет был отдан качеству извлечения договорённостей, а не realtime-скорости.

Возможные будущие улучшения:

- GPU inference;
- меньшая локальная модель;
- более быстрый hosted LLM;
- structured generation;
- оптимизация prompt;
- уменьшение context;
- более специализированная модель для extraction.

# Обнаруженные проблемы во время разработки

## 1. Возврат старого дедлайна

Ранние версии могли после изменения дедлайна сохранить старый срок.

Например:

```text
Friday → Monday
```

иногда снова превращалось в:

```text
Friday
```

Исправление:

- LLM извлекает события;
- финальное состояние определяется deterministic resolver.

---

## 2. Слабая supporting quote

Ранняя версия могла использовать слишком слабую цитату вроде:

```text
Кей, согласен, не в этот раз.
```

Вместо неё resolver выбирает более прямое доказательство:

```text
Давай не будем сейчас это делать, отложим на потом.
```

---

## 3. Несоответствие цитаты и таймкода

Раньше правильная цитата иногда могла получить таймкод другой реплики.

Исправление:

- supporting quote ищется в исходном transcript;
- timestamp берётся именно из найденной реплики.

---

## 4. Относительные даты

Формулировка:

```text
на следующей неделе
```

не должна автоматически превращаться в абсолютную дату.

Теперь исходная относительная формулировка сохраняется.

---

## 5. Topic fragmentation

Test 3 показал ещё одну проблему.

Одна задача могла появиться под немного разными названиями.

Например:

```text
проверка формы обратной связи
```

и:

```text
проверка формы обратной связи до пятницы
```

могли ошибочно восприниматься как разные задачи.

Также AssemblyAI искажал слово `pricing`:

```text
pricing
причин
причинг
```

Для контролируемого сценария в resolver была добавлена canonical topic normalization.

---

# Robustness к ошибкам распознавания речи

ASR может искажать:

- английские слова;
- названия продуктов;
- технические термины;
- имена.

Пример из Test 3:

```text
pricing
```

распознавался как:

```text
причин
```

или:

```text
причинг
```

Текущий resolver содержит ограниченный набор deterministic normalization rules.

Для production-версии понадобился бы более общий механизм semantic entity resolution.

# Ограничения

Это прототип, а не production meeting platform.

Текущие ограничения:

- в основном тестировались контролируемые русскоязычные разговоры;
- основной сценарий — короткие записи;
- локальный qwen2.5:7b может работать медленно на CPU;
- качество speaker diarization зависит от качества записи;
- ASR может искажать технические слова;
- topic normalization пока частично rule-based;
- таймкоды evidence относятся к целой реплике, а не к точной границе отдельного предложения;
- относительные даты не преобразуются без calendar context;
- нет пользовательских аккаунтов;
- нет базы данных встреч;
- нет production storage;
- нет calendar integration;
- нет Jira / Trello / Notion integration;
- используется локальный Flask development server.

---

# Что находится вне scope

В рамках текущего задания система не отправляет задачи автоматически в:

Основная цель — правильно определить финальные договорённости из разговора.

# Test 3 — неоднозначность

Содержит условную фразу:

```text
Я, возможно, посмотрю завтра, если закончу текущие задачи.
```

Но позже явно сказано:

```text
Тогда пока не фиксируем это за тобой.
```

И финально:

```text
По pricing-блоку тогда вернёмся позже, когда будет понятно, кто сможет заняться.
```

Ожидаемый результат:

```text
UNRESOLVED

Обновление pricing-блока на лендинге

Owner: missing
Deadline: missing
```

Критический false-positive:

```text
Обновление pricing-блока → Оксана → завтра
```

не должен появиться.

Фактический результат:

```text
PASS
```

# Итог

Прототип демонстрирует подход, в котором AI используется не как обычный meeting summarizer, а как часть системы отслеживания состояния договорённостей.

Ключевая идея:

```text
Understand with AI.
Resolve state deterministically.
Show evidence.
```

То есть:

- AI понимает разговор;
- код определяет финальное состояние;
- пользователь может проверить результат по исходной записи.
